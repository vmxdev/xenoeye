# Анализ исходного проекта Xenoeye

## Назначение

Xenoeye — высокопроизводительный коллектор и анализатор NetFlow v5/v9, IPFIX и sFlow. Ядро написано на C и рассчитано на обработку большого количества потоков с минимальными накладными расходами. Оно принимает телеметрию, применяет фильтры объектов мониторинга, агрегирует временные окна, рассчитывает скользящие средние и формирует SQL-файлы для PostgreSQL или ClickHouse.

## Исходная архитектура

До добавления портала проект состоял из одного исполняемого контура:

1. `pcapture.c` и `scapture.c` принимают пакеты через pcap или UDP-сокеты.
2. `netflow.c`, `netflow-templates.c` и `sflow.c` декодируют протоколы.
3. `filter*.c`, `iplist.c`, `geoip.c` определяют принадлежность потока объектам мониторинга.
4. `monit-objects-fwm.c` агрегирует данные в фиксированных окнах и создаёт SQL.
5. `monit-objects-mavg*.c` рассчитывает скользящие средние и запускает реакции на пороги.
6. `scripts/xe-dbexport-pg.sh` импортирует накопленные SQL-файлы в PostgreSQL.
7. Grafana использовалась как внешний интерфейс, без пользователей и разграничения доступа на стороне Xenoeye.

## Выявленные ограничения

- Нет собственного HTTP API и формального контракта с интерфейсом.
- Нет личных кабинетов, ролей и изоляции данных разных заказчиков/подразделений.
- Доступ Grafana к БД сложно ограничивать на уровне отдельных динамических таблиц.
- Строка подключения PostgreSQL была жёстко записана в экспортном скрипте.
- Исходный Compose не разворачивал единый законченный продукт с API и portal UI.
- Установка web-компонентов и их systemd-сервисы отсутствовали.

## Принятое решение

Сетевое C-ядро не переписывается и рассматривается как отдельный back-end collector. Рядом добавлен management/data API на FastAPI. Он читает созданные коллектором таблицы, а собственные учётные записи хранит в том же PostgreSQL в таблицах с префиксом `xe_portal_`. React-приложение обращается только к API и не имеет прямого доступа к БД.

Такое разделение сохраняет производительность и совместимость существующего коллектора, но формирует чёткие границы:

- Collector core отвечает только за приём и вычисления.
- Portal API отвечает за аутентификацию, авторизацию, безопасные запросы и пользовательские настройки.
- Portal UI отвечает за визуализацию и управление личными кабинетами.
- PostgreSQL остаётся общей точкой данных, но доступен только back-end сервисам.

## Совместимость

Формат `xenoeye.conf`, `devices.conf`, объектов мониторинга, фильтров и SQL-таблиц не изменён. Изменение `xe-dbexport-pg.sh` обратно совместимо: без переменных окружения используется прежний DSN `postgresql://xenoeye:password@localhost/xenoeyedb`.
